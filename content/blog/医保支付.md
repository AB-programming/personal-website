# 一、引言：为什么医保支付值得写？
医保支付是整个支付领域里面比较复杂和严谨的一个分支，几乎每个做过这套对接的人，都遇到过各种各样的失败订单，要调用各方日志排查，捋清思路。

笔者目前从事支付行业，站在支付平台的角度，梳理清楚医保支付的整个流程。支付平台夹在HIS与医保平台之间，可以更清晰地做支付流程拆解。理清楚医保支付的大致流程思路和逻辑、理解里面更多的细节，会对支付行业的认识和解决问题有更好的帮助，也可以帮助大家更好地科普医保支付。

# 二、医保支付全景
保支付不是“另一种收单”，如果把微信支付比作一条高速公路，用户扫码后资金从C端流向B端，简单、高效、实时。那医保支付就是一座立交桥群，车流来自不同方向，在多个节点分流、校验、再汇合，最终才完成一次完整的支付闭环。

下面我从以下几个维度拆解这座立交桥。

## 1、六层参与者，缺一不可

**第一层：国家医保局。** 制定医保行业的接口标准、数据规范和清算规则。它是所有医保交易的规则制定者。全国的电子医保凭证、全国统一的医保信息平台，都是它在推动。

**第二层：省级医保平台。** 国家医保局的标准到这里变成了省级实施，各地会根据省内的情况做定制。

**第三层：地市经办机构。** 定点医院、药店的签约管理、每笔交易的试算与结算审批、资金清算，都由地市层级完成。一个省十几个地市，每个地市的医保政策都可能不同，例如起付线、报销比例、药品目录等。

**第四层：定点医疗结构。** 它们是交易的发起方，例如医院的HIS系统生成结算单，药店POS发起个账扣款。

**第五层：ISV/服务商。** ISV负责连接HIS系统和医保业务。ISV中有**支付平台**和**地市服务商**。支付平台负责连接HIS系统和医保平台，处理HIS方发起的结算请求，将医保交易部分上送省医保平台，将自费部分自行处理。地市服务商连接医保平台和金融支付侧，负责处理省医保平台分发下来的医保个账部分的扣款请求，将这部分请求上送支付通道。

**第六层：资金清算方。** 资金清算方包括了银行卡清算通道和三方支付通道。对于医保个账扣款，需要收单方、银联以及发卡银行这个银行卡清算通道进行处理，对于医保自费部分，需要微信/支付宝这样的三方支付通道进行处理。

## 2、三流模型，一笔交易的解剖图

**信息流-数据是交易的血脉**

信息流的核心载体是**结算单**，一笔门诊结算单通常包含：就诊流水号、患者身份信息、费用明细、医保类型等。
信息的流向路径是：HIS生成结算单->ISV转发->医保平台接收->医保平台试算并返回分摊结果->ISV解析->HIS展示给患者确认->正式结算->结果回写HIS。
这条链路上任何一个字段缺失或编码错误，都会导致试算失败，ISV往往要在中间做一层映射。

**资金流-钱分三路**

这是医保支付与三方支付本质的区别。医保支付的资金分为个账支付、统筹报销和自费三部分。

统筹基金是用人单位和职工共同缴纳的医保基金中划入社会统筹的那一部分，它是全体参考人共有的资金池，核心逻辑是互助共济。个人账户是参保人个人名下的医保资金账户，本金和利息归个人所有，可以结转使用和继承。自费分为完全自费和个人负担部分的自费，不在医保目录内的药品，需要完全自费，统筹报销后剩余部分可以选择自费、个账支付或部分自费。

一笔500元门诊费用，医保结算后拆成三笔。统筹报销400元，这400元就从统筹基金中扣除，本质上统筹资金池系统内部的一个记账操作，不涉及跨机构的资金划拨。剩下的100元需要自行支付，这100元可以选择从个人账户扣除，也可以选择自费（例如使用微信或者支付宝支付），也可以选择组合支付（一部分从个人账户扣除，另一部分自费）。

**业务流-支付嵌入就医全流程**

医保支付并不是独立存在的，它嵌入在患者的就医路径中，每一步都耦合。

挂号阶段，需要判断医保类型，是否享有门诊统筹和门诊慢特病的待遇。

就诊阶段，医生开处方时，HIS还需要实时校验药品是否在医保目录内。

结算阶段，HIS上传结算单，进行预结算，患者确认后再进行正式结算和扣款。

退费阶段，分为整单退和部分退，分别要处理个账返还、统筹返还和自费原路退回。

## 3、与三方支付的差异

（1）交易模型不是“扣钱”而是“算账”

三方支付的核心动作是pay，传入金额，扣款。医保支付的核心动作是preSettle，传入结算单，算出一个分摊方案，患者确认后再进行结算，本质是先算后付。

（2）资金归属：钱分属不同主人。

三方支付的钱是用户的，扣到商户。医保支付的统筹基金是全体参保人的共有资金，个账是个人资产但限制用途。

（3）清算周期：T+1而不是实时

微信、支付宝的资金到账以分钟计。医保支付的统筹部分以天计。当天所有交易汇总成对账文件，地市经办审核后拨付。

（4）地市差异：没有“一套代码全国通”

微信和支付宝的API全国统一接入。医保支付同一个省的不同地市，接口版本不同、参数结构不同、报销算法不同。

（5）退费的复杂度

三方支付退款，原路返回，一步完成。医保退费，先判断是整单退还是部分退，个账部分要退回个人账户，统筹部分要冲销医保基金记录，自费走通道方退款。

# 三、三大场景拆解

## 1、场景一：医院场景

患者到医院就诊，典型路径是：挂号 → 候诊 → 医生开具处方/检查/治疗 → 收费窗口（或自助机）结算 → 取药/做检查。结算环节是支付平台介入的核心节点。HIS系统汇总本次就诊的全部费用明细，生成结算单，发起医保支付。

## 2、场景二：药店场景

患者持处方（或直接购买非处方药）到定点药店购药。药店场景的核心差异在于：没有 HIS 系统，没有复杂的住院逻辑，结算流程相对简洁。但"简洁"不等于"简单"——药品目录的匹配和处方外配的合规校验，是药店场景的特有难点。

药店通常通过 POS 机或者药店管理系统发起结算请求。走医保的部分以个账支付为主（统筹在药店场景的覆盖范围有限，主要是个账），自费部分走现金或扫码。

## 3、场景三：医保移动支付

患者通过医院的微信公众号、小程序或 App 完成线上挂号、缴费，无需到窗口排队。这是三个场景中最"像互联网支付"的一个——用户体感上接近于一次电商支付。但对支付平台来说，它的复杂度远超电商：一笔支付要同时协调医保体系和金融支付体系两个完全不同的世界。

# 四、核心基础设施：医保电子凭证

医保电子凭证解决的问题是证明患者身份、钱在哪个账户下。它是国家医疗保障局统一签发的、全国通用的医保身份电子标识。它的出现让“刷实体社保卡”这件物理动作变成“亮一个动态码”的数字动作。

医保电子凭证有以下几个关键的点，它由国家医保局统一签发、与实体社保卡唯一绑定、跨区域互认并且可以在国家医保服务平台APP、微信、支付宝等渠道激活领取。电子凭证是实体医保卡的线上形态，是全国统一的医保身份底座。

| 维度   | 实体社保卡    | 医保电子凭证     |
| ---- | -------- | ---------- |
| 形态   | 实体卡      | 动态二维码/条形码  |
| 携带   | 需随身带卡    | 手机即有       |
| 异地   | 早年“卡不对版” | 全国互认       |
| 线上支付 | 不支持      | 支持（移动支付基础） |

## 1、码的形态与生成：为什么是“动态”的

患者亮出的码，本质是一段经过国密签名、带时效的凭证数据，编写成二维码或条形码来展示。

*   动态刷新，分钟级过期。码里的时效字段很短，几分钟刷新一次。
*   双模式：二维码+条形码。医院和药店的扫码设备都五花八门，有的老式扫码枪只认一维条形码、不认二维码。一般平台上调起的医保电子凭证都包含条形码和二维码两种形式。

## 3、在支付流程里的角色：身份入口

医保电子凭证在这条链路里是**身份入口**，不是支付工具。它既不是账户，也不是扣款指令，它是一张**一次性**的**身份兑换票据**，支付平台拿它换回账户信息，换完即作废。

上面解释了码的形态，因为电子医保码是动态的，所以电子医保码的使命从支付平台解码完成的那一刻就结束了，在后面码已经退出了支付链路，这笔账单只剩下订单和身份信息。

熟悉OAuth 2.0授权码模式的可能感觉会有一些类似，因为OAuth 2.0授权码的基本流程是拿code来换取access\_token，后续的认证都是通过令牌完成，我们可以比较两者：

![OAuth授权码与医保电子凭证的角色类比](/images/2026-11-13/OAuth授权码与医保电子凭证的角色类比.png)

医保电子凭证这样设计有很多好处，如：

- 最小身份披露：不显示证件号、姓名和账单等
- 防止重放：动态码的一次性和短时效可以避免截屏盗刷
- 患者无感：无需实体卡，无需报证件号，扫码即完成身份出示

# 五、支付平台技术

## 1、支付平台内部的状态机设计

状态机的设计是支付平台设计的关键一环，普通的电商支付的内部状态机设计一般如下：

![电商支付状态机](/images/2026-11-13/电商支付状态机.png)

医保支付相比普通电商支付，有着本质区别：它不是简单的“用户-商户”两方模型，而是“参保人-医疗机构-医保基金”三方博弈，有统筹支付、个人账户和自费三条资金通道。这意味着支付状态机不仅要管理订单的生命周期，还要追踪每一笔资金的去向。因此，医保支付的状态机设计不能照搬普通的电商支付。以下两个场景会影响医保支付的状态机设计

- 多资金通道并行：一笔处方费用可能同时从统筹基金、个人账户和自费三个通道扣款，三个通道各自独立结算，任一失败都需要整体回滚，因为需要有全额支付成功和部分支付成功两种状态。
- 结算与支付分离：患者在医院的实时结算只是“预结算”，先将算出的账单（统筹报销金额、个人自费金额）经用户确认后正式结算。医保统筹基金真正的基金拨付也发生在T+N日后。

基于上述分析，医保支付的内部状态机设计可以参考如下：

![医保支付状态机设计](/images/2026-11-13/医保支付状态机设计.png)

下面解释以下上述状态机的设计思路（站在支付平台的角度设计此状态机）。

*   订单创建后状态变为INIT，此时代表订单信息已生成入库。
*   HIS或医保移动支付发起预结算调用，状态更改为SETTING，此时代表已受理预结算。
*   状态改为SETTING后，调用省医保平台进行预结算业务，省医保平台受理后校验医保药品目录、起付线以及报销比例等。如果账单不合规或出现接口超时等问题时，状态改为交易关闭，并向HIS返回详细信息。
*   HIS成功拿到预结算信息后，等待用户确认，用户确认后，状态改为PAYING开始正式结算。站在支付平台上，正式结算分两个通道进行，分别是医保费用和非医保费用。医保费用上送省医保平台，包含统筹金额和个账金额；非医保费用即个人自费金额，正常走系统的扣费流程，例如微信、支付宝或平台的账户系统。全部成功后状态改为SUCCESS，全部失败后状态改为FAILED，部分成功后状态改为PARTIAL\_SUCCESS，但PARTIAL\_SUCCESS并不是终态，如果出现部分成功会进行重试，如果补扣成功，状态变为SUCCESS，重试失败或超时就要进行回滚，状态改为FAILED，若重试失败、回滚也失败，这种情况就需要人工后续处理。最终将结果响应或通过回调的形式返回给HIS。
*   状态为SUCCESS时，订单可以进行退款，状态可以变为REFUND和PARTIAL\_REFUND。

接下来根据上述设计思路，用Java实现一个简单的医保支付交易的状态机（状态机的设计参考和仿照了图解支付系统简洁而精妙的状态机设计与实现一文中的例子）。

设计前先思考状态机的设计应该是一个系统内部的状态流转，不能只靠在库表中维护一个状态字段以及从代码中根据业务逻辑去更改数据库表的状态。我们应该定义一个领域模型，并且结合事件驱动来改变状态。

首先，我们先定义一个状态基类和一个事件基类


定义一个状态事件对类

```java
import java.util.Objects;

/**
 * 状态事件对
 */
public class StatusEventPair<S extends BaseStatus, E extends BaseEvent> {
    private final S status;
    private final E event;

    public StatusEventPair(S status, E event) {
        this.status = status;
        this.event = event;
    }

    @Override
    public boolean equals(Object obj) {
        if (this == obj) return true;
        if (!(obj instanceof StatusEventPair<?, ?>)) return false;
        @SuppressWarnings("unchecked")
        StatusEventPair<S, E> other = (StatusEventPair<S, E>) obj;
        return this.status.equals(other.status) && this.event.equals(other.event);
    }

    @Override
    public int hashCode() {
        return Objects.hash(status, event);
    }
}
```
定义状态机

```java
import java.util.HashMap;
import java.util.Map;

/**
 * 状态机
 */
public class FSM<S extends BaseStatus, E extends BaseEvent> {
    private final Map<StatusEventPair<S, E>, S> statusEventMap = new HashMap<>();

    public void accept(S sourceStatus, E event, S targetStatus) {
        statusEventMap.put(new StatusEventPair<>(sourceStatus, event), targetStatus);
    }

    public S transition(S status, E event) {
        return statusEventMap.get(new StatusEventPair<>(status, event));
    }
}
```

状态机内部封装了一个Map，可以理解为一个规则表，键为状态事件对，值为要转换的状态，即一个源状态和一个事件可以转换为一个目标状态。accept方法就向状态机中添加这些规则。而getTargetStatus方法就是通过一个原状态和事件获取一个目标状态。

```java
    REFUND("FAILED", "退款成功"),
    PARTIAL_REFUND("PARTIAL_REFUND", "部分退款");
    private static final FSM<PayStatus, PayEvent> FSM = new FSM<>();

    static {
        FSM.accept(INIT, PayEvent.PRE_SETTLE, SETTING);
        FSM.accept(SETTING, PayEvent.CLOSE, CLOSED);
        FSM.accept(SETTING, PayEvent.SETTLE, PAYING);
        FSM.accept(PAYING, PayEvent.PAID_FULL, SUCCESS);
        FSM.accept(PAYING, PayEvent.FAILED_FULL, FAILED);
        FSM.accept(PAYING, PayEvent.PAID_PARTIAL, PARTIAL_SUCCESS);
        FSM.accept(PARTIAL_SUCCESS, PayEvent.PAID_RECOVERED, SUCCESS);
        FSM.accept(PARTIAL_SUCCESS, PayEvent.TIMEOUT_ROLLBACK, FAILED);
        FSM.accept(SUCCESS, PayEvent.REFUND_SUCCESS, REFUND);
        FSM.accept(SUCCESS, PayEvent.PARTIAL_REFUND_SUCCESS, PARTIAL_REFUND);
    }

    PayStatus(String status, String description) {
    }

    public static PayStatus getTargetStatus(PayStatus sourceStatus, PayEvent event) {
        return FSM.transition(sourceStatus, event);
    }
}
```

支付状态枚举类内封装了一个状态机，并且把状态机的状态转换规则在静态代码块中都定义好了。

定义支付领域模型

```java
import lombok.Getter;

import java.util.Objects;

/**
 * 支付领域模型
 */
@Getter
public class PayModel {
    private PayStatus lastStatus;
    private PayStatus currentStatus;

    public PayModel(PayStatus currentStatus) {
        this.currentStatus = currentStatus;
    }

    public void transfer(PayEvent event) {
        PayStatus targetStatus = PayStatus.getTargetStatus(currentStatus, event);
        if (Objects.nonNull(targetStatus)) {
            lastStatus = currentStatus;
            currentStatus = targetStatus;
        } else {
            throw new FSMException("状态转换异常", currentStatus, event);
        }
    }
}
```

## 2、核心接口契约

一套医保支付接口应该如何设计？每个字段为什么存在？

**设计原则**

**原则1：做好幂等设计。** 一笔订单从HIS发起开始，经过层层请求，任何一环出现超时重试，都不能造成重复扣款，支付中台需要做好幂等，HIS请求携带的HIS订单号如果重复，不能作为一笔新订单进行扣款。不同的HIS厂商可以HIS订单号重复，同一家HIS厂商的HIS订单号不能重复。

**原则2：试算和结算要分离。** 在医保支付场景中，试算要和结算分开，试算只是读，把订单中的统筹、个账、自费部分计算出，记录到库中，而结算是要真实落实到统筹记账、个账扣款以及自费金额支付上。结算这个操作需要在试算结果出来后，等待患者确认，患者对于医保报销金额有知情权。

**原则3：结果回传统一走查询+回调双通道。** 医保支付过程中的链路长、环节多，超时是比较常见的事情，支付平台对HIS的结果回传要支持回调和查询两种方式，回调缺失时，HIS靠轮询查询兜底。

原则4：金额用分，状态用枚举。医保结算涉及到统筹、个账、自费三个金额字段，任何的浮点误差的都会导致对账不平。状态字段应该用明确的枚举值，不用数字代号。

**接口清单总览**

支付平台对外暴露6个核心接口：

| 接口     | 幂等 | 说明          |
| ------ | -- | ----------- |
| 结算试算   | 是  | 计算分摊结果      |
| 结算确认   | 是  | 触发实际三条链路支付  |
| 结算结果查询 | 否  | 订单查询，兜底查询   |
| 结算结果回调 | 否  | 结算完成，回调HIS方 |
| 结算退费   | 是  | 三路分退        |
| 退费结果查询 | 否  | 退费订单查询      |

## 3、异常处理三板斧：超时、幂等、部分成功

**（1）超时**

医保支付需要经过三个链路，每一个链路所耗的时间也不同，若自费是微信支付宝主扫收银的方式，患者掏出手机扫码可以需要的时间更长， 需要设置超时时间，超出判为异常。

HIS方调用支付平台时，超时时间应该由支付平台在文档中给出，或者文档中写明传入expire参数，由HIS调用方设置超时时间，超时后HIS方可以认为该笔订单已失败或进行查询补单。

支付平台调用下游服务超时有以下几种处理方式：

*   直接判定失败：到达超时时间，此订单状态置为失败，即使下游在超时时间之后成功了，这笔订单状态在支付平台也不会修改，认定该笔订单状态是超时失败，该场景下出现了患者钱扣了但是交易没成功的情况，需要人工手动调用查询接口确认订单状态，然后调用退费接口进行退款。
*   异步查询补单：到达超时时间后，状态是未知，属于中间态，将中间态通过异步通知给HIS，开启异步查询，设定查询次数。
*   定时任务扫描：与异步查询补单不同，不是立即产生查询任务，而是定时扫描。
*   撤销订单：有些渠道支持撤销订单，到达超时时间可以撤销此订单，此时可以直接判定状态为失败。

最后还是需要人工介入的兜底方案。查询不到的订单，状态是未知，应该进入人工队列，定期处理。

支付平台的超时时间的设计也有一定的原则，**每一层的超时时间必须小于它的调用方**，应该逐层递减，留出冗余处理时间，HIS设置的超时时间 ≥ 支付平台设置的超时时间+支付平台的处理时间。

**（2）幂等**

幂等在医保支付中必须可靠，因为重复结算意味着统筹基金重复记账、个账重复扣款，因此设计好幂等在医保支付中尤其重要。

幂等的设计方案：

第一：数据库唯一索引用来兜底，可以使用交易流水号+操作类型作为幂等，操作类型为结算确认、退货。

例如结算表如下：

```sql
CREATE TABLE settle_record
(
    id             BIGINT PRIMARY KEY,
    trans_sn       VARCHAR(64) NOT NULL,
    operation_type VARCHAR(16) NOT NULL, -- 操作类型，CONFIRM/REFUND
    status         VARCHAR(24) NOT NULL,
    ...
    CONSTRAINT uk_settle UNIQUE (trans_sn, operation_type)
);
```

数据库的唯一索引保证了结算时操作物理上只可能有一条执行记录。

第二：状态机检查，通过业务状态的单向流转特性来实现天然幂等。在支付平台内部的状态机设计中已经巧妙的解释了状态机的一些基本原理，通过事件和状态推动规则可以很好的实现幂等。

第三：幂等Token/令牌机制，可以通过申请Token和携带Token两步来保证幂等。原理如下：

*   客户端在执行操作前，先向服务端申请一个全局唯一的Token，Token可以存入缓存中
*   客户端发起业务请求时携带该Token
*   服务端从缓存中校验Token是否存在，若存在就执行业务并且**原子性**地删除Token，若不存在就说明是重复请求，直接拒绝

![token超时](/images/2026-11-13/token超时.png)

第四：乐观锁/版本号控制，可以通过数据版本字段来控制更新操作的幂等。原理是在数据库中增加version字段。更新时带上版本号，更新的SQL语句形如：

```sql
UPDATE settle_record SET status = 'SUCCESS', version = version + 1
WHERE trans_sn = ? AND version = ?;
```

这样只有版本号匹配的时候才会更新成功，否则影响的行数是0，没有更新，可以视为重复或者过期请求，避免了使用悲观锁产生的性能开销。

第五：可以使用去重表来实现，建立一张专门的请求日志表，用请求的唯一标识（如交易流水号）作为主键，每次处理请求前先查表，若记录存在则可以跳过，否则就插入记录并执行业务，但是这需要将查表+插入+业务操作在同一个事务中完成。

**（3）部分成功**

医保支付中，部分成功是常见的，对于很多三方支付，一笔订单，要么成功要么失败。但是医保支付一笔结算，分为三路资金并行，三笔独立成功的概率相乘才是整笔结算的成功概率。

部分成功的几种组合以及处理方式如下：

*   统筹、个账成功，自费失败（用户取消/超时）。可以挂起等待患者重新支付自费或者更换支付渠道。
*   统筹、个账成功，自费失败（技术故障）。重试自费，若持续失败则整单撤销。
*   统筹、个账失败，自费成功。应该选择撤销自费订单，重新交易。
*   个账、自费成功，统筹失败。应该退回个账部分、撤销自费订单，一笔医保的订单只发起一遍统筹记账。
*   统筹、自费成功，个账失败（技术故障/未知异常）。个账重试，若持续失败则冲销统筹、撤销自费订单。
*   统筹、自费成功，个账失败（余额不足）。余额不足的情况下，应该把剩余的钱换成自费处理。

统筹和个账部分失败了应该整体撤单、进行交易冲正，自费失败相对容易处理，明确重试失败后可以重新发起订单或者更换支付渠道进行处理，或者也可以选择撤销整笔订单，统筹和个账分别冲正的处理方式。

日常交易过程中，发生部分成功异常频率较多的情况是医保平台系统网络波动、地址服务商出现技术故障、个账余额不足以及自费过程中用户挂起已经系统异常等。处理起来的策略是能自动的自动，该人工的人工。对于不同的情况处理的方式也应该不同，统筹失败要整笔撤销，个账和自费失败的情况要分为个账失败是业务型还是故障型，如果是由于余额不足或者用户挂起等业务型，应该引导拉起重付或切换渠道尝试，如果是由于网络波动、系统异常等导致的故障型，应该先重试，若持续失败，才将整笔订单撤销。整个过程中部分成功这种异常情况应该记录日志，便于排查。

# 六、医保支付 vs 三方支付（深度对比）

本文不做哪个更复杂的比较，而是要说明，二者解决的不是同一类问题，三方支付解决的是资金怎么搬，医保支付解决的是这笔钱由谁付（统筹、个账、自费）、按什么规则付，然后各路结算。

| 维度     | 三方支付          | 医保支付                     |
| ------ | ------------- | ------------------------ |
| 要解决的问题 | 把钱从付款账户搬到收款账户 | 先判断资格与分摊规则，再完成多路出资       |
| 付款人    | 下单即确定         | 结算时才确定（个账、统筹基金、患者自费）     |
| 身份     | 账户标识，支付机构识别   | 向医保平台兑换身份与参保资格           |
| 金额     | 商户给定          | 计算报销规则，医保侧返回实付           |
| 资金来源   | 余额/银行卡        | 多路并行：个账、统筹、自付（余额/银行卡）    |
| 结果形态   | 成功/失败         | 允许部分成功                   |
| 对账对象   | HIS方和资金流水（两方） | HIS方，医保结算流水，自费资金流水（三方）   |
| 失败补救   | 关单、重试、原路退款    | 结算冲正、退费重结、部分退、跨结算周期处理    |
| 订单数据属性 | 交易数据+账户信息     | 叠加符合基金监管要求的身份、参保、就诊等个人信息 |

# 七、趋势

《医疗保障信息平台 便民服务相关技术规范》（GB/T 45938—2025）已于 2026 年 1 月 1 日起实施，是医疗保障领域的首项国家标准。它规定了医保码（医保电子凭证）、医保移动支付、医保电子处方、个人医保信息授权查询等便民服务的接入方式、功能要求、性能要求与安全要求，适用对象明确包含定点医药机构、合作金融机构与第三方支付机构。规范与标注逐渐形成统一，各个接口逐渐可以抽成稳定层。

刷脸支付、一码支付、移动支付、信用支付四类便捷支付正在融合互补、分别落地：刷脸换掉了展码动作；一码支付把医保报销、个账支付与个人负担压进一次展码；移动支付把流程整体搬到线上；信用支付则由银行授信先行垫付个人负担部分，实现“先看病、后还款”。

电子处方流转、线上挂号、住院预缴与出院结算逐步打通，支付不再集中在窗口那一秒，而是散落在挂号、检查、取药、出院等多个节点。

刷脸、一码、移动、信用支付会让开头那两秒继续变短，短到患者甚至感觉不到支付这件事发生过。但患者侧每少做一步，中间层就要多做完一步：身份仍要核验，账仍要算，多路资金仍要合回同一张账单，出了问题时仍要说得清是哪一环。**技术演进真正抹掉的从来不是复杂性，而是复杂性的可见性。**
